## Common authority, transport and parameters

Every command in this note invokes `TeamsCmdlet.PerformAuthorization(CmdletName)` with its default `Endpoint.MsGraphEndpointResourceId`. That method resolves `TeamsPowerShellSession.GetResource`, obtains a token for that resource with `ModuleConfiguration.DefaultScopesForGraphAPI`, and constructs an authorized client. There is no additional per-command scope argument or ConfigAPI discovery here. Use the SDK's Graph audience/profile boundary, commercial origin `https://graph.microsoft.com`; other cloud origins are selected by shared auth/routing evidence, never by rewriting the strings in this note. Owner/member binding strings in B separately hard-code the commercial Graph origin, which leaves sovereign payload parity unqualified. Sources: B `TeamsCmdlet.PerformAuthorization`; [HTTP routing](../http/routing-evidence.md), [auth capabilities](../auth/capability-evidence.md).

All operation routes below begin `/beta` unless explicitly marked `/v1.0` for user lookup. GET/DELETE requests have no body; mutations use UTF-8 `application/json`. All parameters listed are strings; required parameters are marked `!`. Their values default to null in the CLR models. Parameters are named and accept pipeline property input, except `Get-TeamChannel.MembershipType`, `Set-TeamChannel.NewDisplayName`, and `Set-TeamChannel.Description`, which do not. There is no `SupportsShouldProcess`, `WhatIf`, or `Confirm` attribute on these cmdlets. No binary length/regex/GUID validator is attached to their string identifiers or channel names. `ValidateSet` restrictions are case-insensitive. Sources: B each command's property attributes; runtime snapshot.

The routes record logical segments/query values. Go must encode each path segment and OData string literal separately through the established transport, including doubling embedded OData apostrophes; B's raw concatenation is not permission to reproduce query/path injection. This is an SDK safety decision under the existing [routing contract](../http/routing-evidence.md), not a claim that B already escapes these inputs.

### Sharing creation and update: assessed, not declared unavailable

The current [beta sharing resource reference](https://learn.microsoft.com/en-us/graph/api/resources/sharedwithchannelteaminfo?view=graph-rest-beta) lists List, Get, Delete and ListAllowedMembers; it provides no Create/Update REST operation link. The [channel method index](https://learn.microsoft.com/en-us/graph/api/resources/channel?view=graph-rest-beta) likewise lists sharing reads and unshare. That is evidence about those reference pages, not proof that no mutation exists.

Counter-evidence exists: Microsoft publishes [New-MgBetaTeamChannelSharedWithTeam](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.beta.teams/new-mgbetateamchannelsharedwithteam?view=graph-powershell-beta) and [Update-MgBetaTeamChannelSharedWithTeam](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.beta.teams/update-mgbetateamchannelsharedwithteam?view=graph-powershell-beta). These current Graph-module wrappers accept a SharedWithChannelTeamInfo body (fields include displayName, id, isHostTeam, tenantId, team and allowedMembers); create takes team/channel IDs and update additionally takes the sharing identity. They are **not MicrosoftTeams 8.1.0 commands** and their generated descriptions do not establish accepted service fields, HTTP success/error semantics, cloud availability, permission requirements or invitation/consent workflow.

Implementation disposition: reserve `ChannelShares.Create` and `UpdateByID` as **unsettled candidate operations**, do not emit requests until service REST or verified first-party implementation evidence supplies the complete mutation contract. Do not mark them unsupported, substitute channel creation for sharing an existing channel, or treat renaming a team as updating a sharing relationship. Closure requires tracing those published wrappers to actual request construction plus authoritative service acceptance/authorization semantics. [Sharing change notifications](https://learn.microsoft.com/en-us/graph/teams-changenotifications-channelmembership) demonstrate that sharing relationships can be created, but their POST is to `/subscriptions`, not evidence for a sharing POST endpoint.


```json
{"members":[{"@odata.type":"#microsoft.graph.aadUserConversationMember","user@odata.bind":"https://graph.microsoft.com/beta/users('00000000-0000-4000-8000-000000000001')","roles":["owner"]}],"displayName":"Synthetic","description":"","membershipType":"Private"}
```

Null description, members, IDs, tenant ID and OData ID are omitted. An empty description remains `""`. `Owner != null` triggers lookup/member construction, even when empty. Do not invent a successful service result for that inconsistent request. Owner GUIDs are normalized with `Guid.ToString`; other strings use the user resolver below. The owner model's serialization callback adds the three extension fields shown, suppressing its inherited user ID and roles properties. Sources: B NewTeamChannel nested models/ProcessRecord; S.

B `SetTeamChannel.TeamChannelModelForPatch` assigns `displayName=NewDisplayName`, `description=Description`, leaves `id=null`; helper null suppression means omitted values do not clear fields. S: no fields gives `{}`, empty Description gives `{"description":""}`. B still sends `{}`; service acceptance is not observed. Proposed Go `ChannelPatch` needs optional string fields (nil=omit, pointer to empty=explicit empty), not plain strings with `omitempty`; explicit JSON null is not a demonstrated compatibility input.

After filtered lookup, Add with omitted Role constructs:

```json
{"@odata.type":"#microsoft.graph.aadUserConversationMember","user@odata.bind":"https://graph.microsoft.com/beta/users/<User>","roles":["member"]}
```

## Lookups, paging and output projections

For Get/Add/Remove-TeamChannelUser the initial GET is `/beta/teams/T/channels?$filter=tolower(DisplayName) eq tolower('<name>')`. It reads **one page**, takes item zero without further name matching, and throws local `ApiException(404,"Channel not found")` on null response/value or zero items. Add and Remove then reject Standard with local status 403. Get does not reject Standard. Set/Remove-TeamChannel use one unfiltered first page and ordinal case-insensitive comparison; missing match produces the same local 404. A match on a later page is not searched. Sources: B these five ProcessRecord methods. Proposed adapters must keep explicit compatibility tests for the first-page limitation; a deliberate full-page resolver is a separately documented behavior improvement.

B `Utils.UserUtilities.GetMembershipIdFromUserIdOrUPN` has two paths:

- Private channel: non-GUID User is resolved; membership ID is locally computed as base64(UTF-8(`channel.Id + "##" + userID`)). A User already recognized as GUID is used as supplied, without canonicalization in this helper.
- Other channel types (in practice Shared after the Standard guard): list all channel members, select first whose email or user ID equals User ignoring case, use the returned member `id`; missing match throws a generic exception. TenantId is not used to disambiguate. Null email handling is not defensive.

Current [list-channel-members](https://learn.microsoft.com/en-us/graph/api/channel-list-members?view=graph-rest-beta) explicitly requires opaque membership IDs. The canonical Go ID-based primitives therefore accept returned IDs; any private-channel ID synthesis belongs only to an explicitly characterized compatibility path and remains a current-service acceptance risk.

B `Utils.GraphUtilities.GetUserId(httpClient, upn, graphResource)` first issues direct GET `/v1.0/users/<upn>`. On HTTP 404 only, it tries GET `/v1.0/myorganization/users?$filter=mail eq '<upn>'` and takes the first value from its **first page**. Otherwise it reports the original response status/error. This fallback route is established by B, but current support/permissions for the historical `myorganization` alias have not been qualified. It is used by non-GUID Owner, non-GUID associated-team User, and private-channel membership lookup.

B `HttpUtilities.GetAll<T>` repeatedly deserializes `PageResponse<T>` (`value`, `@odata.nextLink`, `@odata.count`) and follows nextLink until null/whitespace. It has no explicit page-size query, maximum page count, loop check, host check or partial-result return. List commands and shared roster resolution use it; the name lookups above do not. Go uses the existing bounded, origin-validated pagination contract. Null/missing `value` is not evidence of an empty successful collection because B would fail adding it. Sources: B Utils.HttpUtilities.GetAll, Model.PageResponse; [HTTP pagination](../http/pagination-evidence.md).

B `UserUtilities.GetUsersToOutputFromGraphAadUsersByRole` first selects requested role or orders owners, then members, then guests, preserving source order within each category. `GraphAadUserConversationMember.GetRole` gives owner precedence over guest, case-insensitively; absent/empty/unrecognized roles become Member. It constructs `UserInfo` or `UserEnhancedInfo` with `User = userPrincipalName ?? email`, then calls `GraphUtilities.GetUpnForUsers` **even for already populated UPNs**. The helper issues GETs `/beta/users?$select=id,userprincipalname&$filter=((id eq '<id>')or...)` in groups of at most ten (first chunk can be shorter, because its counter starts at count−1), follows pages, and overwrites User when the result includes the ID. These are multiple filtered GETs, not Graph `$batch`. A lookup failure fails the command; there is no best-effort catch. Duplicate returned user IDs can fail dictionary insertion. Cross-tenant members may not have a corresponding host-directory user; no result preserves the initial UPN/email. Sources: B UserUtilities/GraphUtilities.

## Async, retry and failure contracts

Standard/private New-TeamChannel uses `HttpUtilities.Post<T>`, accepting any success status and decoding a nonblank body; empty success returns null. Shared uses `PostToAPIWithLocation`, accepting any success status, returning `Headers.Location.ToString()` and ignoring the body. The output field is confusingly named `TargetResourceLocation` although the header represents the **operation** location. Missing Location would fail locally. No creation branch polls. Current [create-channel](https://learn.microsoft.com/en-us/graph/api/channel-post?view=graph-rest-beta) specifies 201 plus channel for standard/private and 202 plus operation link for shared. A Go result must distinguish completed Channel from accepted Operation; it must not treat Location as the created channel.

Get-Operation returns B `Model.TeamsAsyncOperation`: `id`→OperationId, `operationType`→AsyncOperationType, `status`→AsyncOperationStatus, `createdDateTime`, `lastActionDateTime`→LastUpdateDateTimeUtc, `attemptsCount`, `targetResourceId`, `targetResourceLocation`. Pinned enum operation names are Invalid, CloneTeam, ArchiveTeam, UnarchiveTeam, CreateTeam, TeamifyGroup, CreateChannel; status names Invalid, NotStarted, InProgress, Succeeded, Failed. The pinned model has **no error property**, and uses closed string-enum conversion. Proposed Go wire type retains string states/types and `error` diagnostics; unknown state cannot imply completion. Sources: B Model.TeamsAsyncOperation/AsyncOperationType/AsyncOperationStatus; current [operation resource](https://learn.microsoft.com/en-us/graph/api/resources/teamsasyncoperation?view=graph-rest-beta).

The current [Get teamsAsyncOperation page](https://learn.microsoft.com/en-us/graph/api/teamsasyncoperation-get?view=graph-rest-beta) documents chat operations and chat permission tables, not the pinned `/teams/T/operations/O` endpoint. It cannot establish team-operation permissions. The team route is proven by B; its exact permission contract remains unresolved. The resource docs establish 202/Location and more than 30 seconds between polls. Use the existing [operation waiter](../http/operation-evidence.md) with explicit **beta** status routing; never use the foundation's v1.0 default to silently change this command's route or replay creation.

B shared HTTP helpers retry statuses 408,429,500,502,503,504 up to five retries, use Retry-After delta or incorrectly use the DateTimeOffset offset for date-form Retry-After, otherwise jitter with one-second median seed. This applies indiscriminately to helper GET/POST/PATCH/DELETE. The direct Add-member POST and direct initial UPN GET bypass this helper policy. These are observed legacy behaviors, not proof of replay safety. Go retains its safer shared retry budget: reads may replay; mutations require explicit evidence of safe replay, which this research does not provide. Sources: B Utils.HttpUtilities.SendRequest and Common.HttpStatusCodeGroup; [HTTP retry evidence](../http-retry-evidence.md).

Helper errors attempt `MSGraphApiErrorRoot`; if parsed, preserve HTTP status and `error.code`, otherwise use raw text in the legacy exception. Add's direct POST reports status/message without separately retaining the code. Go must preserve structured codes/status/correlation through existing redacted `client.APIError`, never copy legacy response/body logging. Local lookup 404 and Standard-channel 403 must be distinguishable from received HTTP responses. No special propagation error, transfer, multipart, remote cancellation, or transaction is evidenced for this subset. Patch/delete helpers ignore successful bodies; standard service status expectations are 204 for channel patch/delete, member delete and unshare, 200 for member patch, 201 for member add.
